**Hub:** [`README.md`](../README.md).

## 1. Why stock 7DTD cannot do this

### What stock already does *not* do

Stock does **not** send every zombie to every player. Relevance is **local**: chunks load around players (view / sim distance), and entity position packages (`NetPackageEntityPosAndRot` and friends) go to clients that need entities in range, not a full N×M mesh. Observer-style filtering also shows up on systems like dynamic mesh.

So the problem at 1k / 10k is **not** “add AOI because vanilla fans out the world.” Vanilla already has **distance/chunk-scoped interest**. The problem is that those mechanisms and the sim behind them were built for **small dozens of players** and **hundreds of AI**, not three orders of magnitude more.

### What actually breaks

Stock dedicated is still roughly:

```text
one Unity main loop
 → gmUpdate / world tick
 → entity list + AI LOD + path queue
 → ConnectionManager pumps NetPackage* for in-range / relevant clients
 → chunks / mesh / saves as shared structures
```

| Subsystem | Stock-shaped cost | At 1k players / 10k AI |
|---|---|---|
| Entity tick | Walk large lists; slice + AI LOD help | 10k OOP entities still crush the main path even if most are “far” |
| Closest-player / AI targeting | Per-entity work toward nearby players | Must stay O(local); any global scan dies |
| Pathfinding | Shared A* worker queue | Permanent blood-moon queue depth |
| Net (per client) | Replicate **in-range** entities + chunks | 1k independent bubbles × dense local fights = huge **aggregate** send/CPU, even with locality |
| Chunk residency | Union of player view/sim bubbles | Spread-out 1k players → enormous unique chunk set |
| GC / heap | Mono + reference-heavy graphs | Churn under spawn/despawn |
| Process model | One authority world, one main loop | No horizontal scale |

### Network math (scoped, not full mesh)

Interest is local. Aggregate cost still scales with **players × (entities in each player’s range)**, not players × global zombies.

Example: each of 1k players has **40** relevant agents streamed at **10 Hz**, **~32 B** useful payload:

```text
1000 × 40 × 10 × 32 B ≈ 12.8 MB/s outbound payload
```

That ignores headers, reliability, chunk/mesh streams, block updates, inventory. It is enough to show: **local interest does not make 1k clients cheap**; it only avoids the absurd full-mesh case (which stock correctly does not do).

If many players stack in one megafight, local density explodes and each client’s “in-range set” becomes huge. If they spread out, **chunk union** and **sim of many semi-active regions** explode instead.

**CPU rule of thumb:** sim and net work must stay **O(local density × participants)**, with hard budgets. Global population is a **cap**, not a per-tick work multiplier.

## 2. Design thesis

```text
1. Spatial index is the spine (every query is local)
 - stock already scopes by distance/chunks; at 1k you need faster, explicit structures
2. Simulation LOD by distance / relevance (most zombies almost sleep)
3. Network LOD mirrors sim LOD (still local interest; tighter rings + rates + budgets)
4. SoA / dense arrays for hot zombie fields (cache), not 10k fat class graphs
5. Command buffers: workers propose, one commit phase applies
6. Pathfinding is hierarchical + shared + rate-limited
7. World streaming is bubble-union with hard caps, not “load everything”
8. Optional: shard by geography when one box cannot hold the union of bubbles
```

Thread-per-zombie still loses (see [`OPTIMIZATION_IDEAS.md`](OPTIMIZATION_IDEAS.md)). Prefer **fixed worker pools + spatial partitions**.

## 3. Core data structures

### 3.1 Entity identity

```text
EntityId : uint32 // dense or generational
Generation : uint16 // recycle safety
Kind : u8 // Player, Zombie, Animal, Projectile, ...
Flags : u16 // Alert, Feral, Dead, Culled, ...
```

**Generational indices** (id + generation) so networked handles and AI blackboards do not point at recycled zombies.

### 3.2 Structure-of-arrays (SoA) for hot zombie state

Fat `EntityAlive` objects are the wrong layout at 10k. Hot path wants:

```text
// Parallel arrays, length = zombie capacity (e.g. 16384)
pos_x[i], pos_y[i], pos_z[i] : f32
vel_x[i], vel_z[i] : f32
yaw[i] : f32
hp[i] : f32 or u16
state[i] : u8 // Idle, Hunt, Attack, Ragdoll, ...
ai_tier[i] : u8 // Full, Medium, Far, Hibernating
target_player[i] : EntityId // or none
path_ticket[i] : u32 // handle into path system
cell[i] : u32 // spatial hash cell
alert_until_tick[i] : u32
```

Cold data (loot tables, name, animation set, rare buffs) lives in **side tables** keyed by id, not in the hot row.

Players can stay more OOP (only 1k, heavy inventory/quests). Zombies should not.

### 3.3 Spatial index (mandatory)

**Uniform grid / spatial hash** (usually better than a deep quadtree for mostly-2D ground agents):

```text
cell_size ≈ 8-16 m (tune to combat range and AOI ring width)
grid : open hash map CellKey → EntityList

CellKey : hash(floor(x/cell), floor(z/cell)) // Y optional bands

Per cell:
 zombie_ids : dense uint32 list (or fixed slab + freelist)
 player_ids : small list
 dirty : bool // moved this tick
```

Operations:

| Query | Use |
|---|---|
| `for_each_in_radius(pos, r)` | AI targets, net AOI, screams |
| `insert/move/remove` | entity motion (only when cell changes) |
| `players_in_cell_ring` | spawn pressure, sleeper wake |

**Closest player for zombie i** must be:

```text
search expanding rings from cell(i) until hit a player or max tier radius
```

Never scan all 1k players per zombie every tick. Cache:

```text
closest_player[i], closest_dist_sq[i], closest_valid_tick[i]
// refresh Full tier every N ms; Far tier every few seconds or on cell change
```

### 3.4 Interest / AOI sets (network + sim)

Per player:

```text
AOI {
 full_radius // combat detail, high rate
 medium_radius // positions lower rate
 far_radius // count/aggregate only or nothing
 visible_entities : dense set or sparse bitset
 last_sent_seq[entity] : for delta compression
}
```

Build AOI from spatial grid each tick or every 2-3 ticks (hysteresis so border thrash dies).

**Bitsets:** if entity ids are dense 0..N, a `BitSet` of size N per player is 10k bits ≈ 1.25 KB → 1k players ≈ 1.25 MB (fine). Membership tests O(1).

### 3.5 Simulation tiers (not one AI for all)

| Tier | Example radius | Rate | Work |
|---|---|---|---|
| **Hibernate** | no player in 128 m+ | 0-0.2 Hz | almost nothing; maybe despawn policy |
| **Far** | 64-128 m | 1-2 Hz | face/walk noise, no path |
| **Medium** | 24-64 m | 5 Hz | cheap steer to last known player cell |
| **Full** | < 24 m or alerted | 10-20 Hz | real combat AI + path tickets |
| **Player** | always | 20-30 Hz | full rules |

Global budget example:

```text
max_full_ai_per_tick = 500
max_medium_ai_per_tick = 2000
max_path_requests_per_tick = 100
max_path_expands_per_ms = ...
```

Priority queue: **alerted near players first**, then distance, then fairness tokens so edge zombies do not starve forever.

### 3.6 Pathfinding structures

Stock global A* on a huge voxel grid at 10k agents fails.

Need **hierarchy**:

```text
Coarse graph : portal / waypoint graph per region or navmesh tiles (tens of m)
Fine grid : local A* only inside a tile or combat pocket

PathTicket {
 agent, goal, status, coarse_nodes[], fine_corridor[], expire_tick
}

PathRequestQueue : priority heap (alert, distance, age)
PathWorkers : fixed pool (CCD-pinned), write results to PathTicket store
```

**Group paths:** zombies with same goal cell within ε share one coarse path; fine steering separates.

**Flow fields** (optional blood-moon mode): for a siege on one base, compute a flow field once per goal region instead of 2000 A* to the same door.

### 3.7 World / chunks

```text
ChunkKey (cx, cz)
ChunkResident {
 refcount_players_in_range
 voxel_slab or section mask
 nav_tile_handle
 sleeper_state
}
```

**Residency = union of player bubbles**, each bubble capped (view distance hard cap).
If 1k players are uniformly spread on a huge map, **unique chunks ≈ 1k × bubble area** and one machine dies. Operational truth:

| Player geography | Feasibility |
|---|---|
| Clumped megasession (events, small map) | One host possible with heroic eng |
| Uniform spread on 10k map | **Shard** by region or refuse |

Optional **shard map**:

```text
ShardId → world AABB
Border halo entities replicated between shards
Players hand off at borders
```

That is multi-process design, not a Harmony mod.

### 3.8 Networking structures

```text
PerConnection {
 ao_i snapshot
 outbound_priority_queue // reliable vs unreliable lanes
 bandwidth_token_bucket
 entity_delta_baseline[EntityId] // last sent pos/hp
}

Packet batching:
 UnreliablePosBatch { tick, count, (id, quant_pos, yaw, bits)... }
 ReliableEvents { damage, death, block change, inventory }
```

Quantize positions (cm or fixed-point). Send **deltas**. Drop far medium-tier updates under bandwidth pressure (evergreen MMO trick).

**Do not** invent io_uring inside Unity for this; if you ever owned the socket layer, a custom UDP pump could use it. That is a greenfield net stack.

### 3.9 Command buffer / parallelism

```text
Worker N:
 reads immutable snapshot S(t) // positions, cells, hp
 writes Intent[] // MoveTo, Attack, PlaySound, RequestPath

Main commit:
 apply intents in deterministic order (by EntityId)
 resolve conflicts (two attacks same target)
 emit net events
 advance t → t+1
```

Snapshot S can be SoA double-buffered. Workers never mutate live world.

### 3.10 Spawning and population control

```text
SpawnBudget {
 global_cap = 10000
 per_player_pressure
 per_biome_cap
 per_chunk_cap
}

DespawnPolicy {
 hibernate far from all AOI
 hard despawn if still unused and pressure high
 never despawn quest-critical without rules
}
```

10k is a **cap**, not a promise of 10k always thinking.

### 3.11 Memory sketch (order of magnitude)

| Structure | Rough size |
|---|---|
| Zombie SoA hot fields (~64-128 B/entity) | 0.6-1.3 MB for 10k |
| Spatial lists overhead | few MB |
| Per-player AOI bitset 10k | ~1.25 MB total |
| Path tickets / corridors | tens of MB if generous |
| Chunk slabs for resident set | **dominates** (depends on bubble union) |
| Player inventories / quests | large but 1k × heavy |

CPU and **chunk residency**, not the 10k float positions, usually dominate RAM.

## 4. Tick schedule (one box fantasy)

```text
each 33 ms frame (30 Hz wall):
 1. ingest inputs / net
 2. rebuild dirty spatial cells
 3. refresh AOI (maybe every 2 frames)
 4. assign ai_tier from AOI + alert
 5. schedule AI jobs under budgets (workers)
 6. path workers drain priority queue
 7. commit intents (main)
 8. physics/combat resolution (main or constrained)
 9. build net batches per connection (workers ok)
 10. send
 11. stream chunks to match residency
 12. save journal async (ops / background)
```

Blood moon: raise Full budget, enable flow fields, temporary cap on far spawns.

## 5. Without geographic sharding (one seamless world)

**Sharding** here means *separate world processes + border handoff*.

**Without sharding** means *one authority, one continuous map, every player in the same session*.

You still use **spatial partitions as data structures** (grids, jobs per cell range). That is not multi-server sharding; it is how one process parallelizes local work.

### 5.1 What must remain true

| Requirement | Implication |
|---|---|
| One rules authority | One deterministic commit order for combat/blocks (or carefully commutative ops) |
| Seamless movement | No unload/reload of the player into another server mid-run |
| Local net interest | Keep stock’s idea: client only gets nearby entities/chunks (already true) |
| 10k AI cap | Most agents **hibernate**; only local density is expensive |
| 1k connections | Net I/O and per-connection serialization must be multi-core |

If players are **uniformly painted** across a huge map, **chunk RAM and disk** still kill a single box even with perfect AI. Single-host seamless assumes either a **bounded playable area**, **strong clumping**, or **very aggressive chunk cold storage** (almost empty slabs far from everyone).

### 5.2 Architecture: one process, phased tick (not one big lock)

```text
 ┌─────────────────────────────────────┐
 │ Single world authority │
 │ SoA entities + spatial hash │
 └─────────────────────────────────────┘
 │
 ┌────────────────────────────┼────────────────────────────┐
 ▼ ▼ ▼
 Net ingress pool Sim workers (read S) Path workers
 (1k sockets) intents only tickets only
 │ │ │
 └────────────────────────────┼────────────────────────────┘
 ▼
 Single commit phase (ordered)
 apply intents → S' → net egress jobs
```

Phases each frame:

1. **Ingress** - many threads read UDP/TCP into lock-free per-connection rings.
2. **Publish snapshot S** - immutable SoA + spatial structure for this tick (double buffer).
3. **Parallel produce** - AI intents, path results, optional net encode of *last* tick’s deltas.
4. **Commit** - one thread (or a short parallel reduce with fixed order) applies intents.
5. **Egress** - many threads build/send per-connection batches from committed state.

No thread-per-zombie. Workers are a **fixed pool** sized to CCD count.

### 5.3 Make 10k zombies cheap without shards

The only single-host trick that works: **almost none of them think.**

| Tier | Share of 10k (example) | Work |
|---|---|---|
| Hibernate | ~80-95% | Not in any player bubble; no path, no net, optional 0.1 Hz bookkeeping |
| Far | ~5-15% | Steering noise, 1-2 Hz, no A* |
| Full | hundreds max | Real combat AI + path tickets |

**Global Full-AI budget** (e.g. 300-800/tick) matters more than the 10k cap.
Hibernate is free if spatial index answers “any player in R?” in O(player cells), not O(zombies).

**Store hibernating agents densely:**

```text
active_set : dense indices into SoA (only non-hibernate)
hibernate_store : compact pos + kind + seed // or even “respawn recipe” not full entity
```

Optional: far from all players, **collapse** to a population counter per cell and **rehydrate** when a player approaches (stronger than LOD; changes world feel).

### 5.4 Parallelism without world shards

| Work | Parallelism | Sync |
|---|---|---|
| Closest-player / tier assign | Over zombie chunks of the spatial grid | Read-only S |
| Full/Medium AI | Job ranges over `active_set` | Intents only |
| Path requests | Worker pool + shared nav tiles (read-only or tiled locks) | Tickets |
| Net encode/send | One job per connection or per N connections | Read committed S |
| Chunk compress/load | Background I/O threads | Hand off ready slabs on commit boundary |
| Combat resolve | Prefer main commit; or parallel by **non-overlapping** spatial bins with a second conflict pass | Hardest part |

**Spatial bin parallel commit** (advanced): partition the grid into tiles; resolve combat inside tiles in parallel; **border entities** (touching two tiles) resolved in a serial rim pass. Still one world, one tick, no player handoff.

### 5.5 Networking for 1k clients on one host

Stock already scopes by range. At 1k you need the *implementation* to scale:

| Piece | Single-host approach |
|---|---|
| Sockets | One thread/event loop is not enough; **multi-threaded or multi-queue** NIC + sharded connection tables |
| Encode | Per-connection jobs; delta + quantize; ring rates |
| Priority | Combat > movement > far cosmetics; drop under `token_bucket` |
| Chunk stream | Queue with per-connection and global bandwidth caps |
| Avoid | Single lock around “send to all relevant clients” for each entity move |

Data structures:

```text
ConnectionShard[K] // K ≈ core count; conn_id % K
 connections[]
 ingress_ring
 egress_ring

EntityObserver reverse index (optional):
 entity_id → small list of connection ids that currently AOI it
 // update when AOI rebuilds; makes "entity moved" fan-out O(observers), not O(players)
```

Reverse observer lists are how you stay local **and** fast when many entities move: each zombie only dirty-notifies the clients that already care.

### 5.6 Chunk / memory without shards

Single host dies on **union of bubbles**. Options that are *not* multi-server sharding:

| Strategy | Idea |
|---|---|
| **Hard view/sim caps** | Small bubbles; non-negotiable at 1k |
| **Cold chunks** | Unload voxel detail to compressed blobs or disk as soon as refcount 0 |
| **Sparse columns** | Don’t allocate full height for empty air (dynamic Y sections) |
| **Population fields** | Far regions store density maps, not full sleeper entities |
| **Playable envelope** | One large but finite “server map” (e.g. 4-8 km) so union is bounded |
| **Instance-lite events** | Same process, temporary high-detail pocket (still one world id) |

If the design requires Earth-scale simultaneous occupancy everywhere, **single host without shards is not honest**. Seamless one-world at 1k implies **bounded concurrent geography** or **extreme cold storage**.

### 5.7 Pathing without shards

- Hierarchical nav on one world graph.
- Cap in-flight path jobs.
- **Flow fields** for horde → single POI.
- Nav tiles loaded with chunk residency; workers only touch resident tiles.
- No per-zombie thread.

### 5.8 Determinism and fairness

Without shards you still need:

- Fixed commit order (entity id).
- Fairness tokens so the same 200 zombies near spawn do not monopolize Full budget.
- Alert/damage always promotes to Full (game feel).
- Bandwidth fairness so one megafight does not starve other connections entirely (or explicitly prefer the fight, as a design choice).

### 5.9 Hardware picture (single box)

| Resource | Role |
|---|---|
| 1-2 CCD for commit + hottest Full AI | Low latency |
| Other CCDs for path + net egress + chunk I/O | Throughput |
| Lots of RAM | Resident chunk union |
| Fast local NVMe | Cold chunk / save journal |
| NIC with multi-queue | 1k concurrent UDP flows |

CCD pin helps; it does not replace SoA + budgets ([`HOST_TUNING.md`](HOST_TUNING.md)).

### 5.10 What you give up (honest)

To stay **one world, one host, no geo-shards**:

| Usually required | Why |
|---|---|
| Aggressive hibernate / rehydrate | 10k cannot all think |
| Smallish view distance | Chunk union |
| Bounded map or clumped play | RAM |
| Simpler far AI | CPU |
| Custom stack (not stock Unity loop) | Main-thread ceiling |
| Possible fidelity cuts under load | Budgets always exist |

You do **not** need multi-server portals. You **do** need a different internal architecture than stock `gmUpdate` + OOP entities.

### 5.11 Relation to stock 7DTD

| Approach | Feasible as Harmony modlet? |
|---|---|
| Tighter LOD / path caps / mesh budgets | Yes (EfficientServer direction) |
| Full SoA + phased workers + reverse observers | **No** (rewrite dedicated) |
| 1k players on stock binary | **No** for real game clients |

## 8. What open-source tools teach about this goal

Public 7DTD tooling (ServerTools, IceCoffee ServerKit, SphereII, CSMM, OCB, MVirus, Allocs, lag-shield, BackupMod, free NAIWAZI pieces) was surveyed for optim lessons. Full notes: [`../../7dtd-engine-research/oss-tools/NOTES.md`](../../7dtd-engine-research/oss-tools/NOTES.md), folded into [`OPTIMIZATION_IDEAS.md`](OPTIMIZATION_IDEAS.md).

| Finding | Implication for 1k×10k |
|---|---|
| **Live sim levers in public mods are almost only “do less”** | Falling-block→air, entity purge, crude zombie caps. Capacity comes from **less work**, not clever panels. |
| **Parallel AI/send is a graveyard** | IceCoffee `PerformanceTuning` is **fully commented out** (Parallel EAI, Parallel SendPackage, concurrent path `Task.Run`, async saves). People try threads, then abandon or sell closed. |
| **NAIWAZI claims threads + gateway** | Closed optim; free AC/Bot only. Gateway helps **sessions/restarts/net ownership**, not free main-thread budget for 10k OOP entities. |
| **Ops scale ≠ sim scale** | CSMM, Allocs map, BackupMod, high-ping kick live outside or beside the tick. They do not multiply `gmUpdate` capacity. |
| **Content can own the frame** | OCB power Update self-warns at **>20 ms**. TE/power/NPC packs blow budgets before “pure AI” math does. |
| **Join/mod bandwidth is its own product** | MVirus: prefer HTTP offload over in-game streams. Isolate from AI tick design. |

**Market signal:** nobody open has shipped MMO-grade 7DTD sim. They shipped admin surfaces and fidelity trades. Treat 1k×10k as **rewrite/shards/product**, and treat OSS as confirmation of the **less-work + hard budgets** doctrine.

## 9. What we can do on the main sim (stock / EfficientServer)

“Main sim” here means the work on the dedicated **main loop path**: `gmUpdate` → world tick → entity activity / slice → AI tasks → path *requests* → commit side effects. Path *compute* is already partly off-thread; net and mesh share the same frame budget.

### 9.1 Ranking (always)

```text
1. Do not simulate (hibernate / despawn / never spawn / hard Full-AI budget)
2. Simulate less often (LOD, tick slice, phase groups, delay)
3. Simulate cheaper (simpler far AI, shared path, cache closest-player)
4. Parallelize what remains (fixed workers + snapshot + deterministic commit)
5. Faster serial remainder (CCD pin, fewer allocs, SoA in a rewrite)
```

Threading only helps after (1)-(3). At 10k Full AI on main, 32 cores do not save you.

**Extract most sim off main and multithread it?** Correct for a **custom dedicated** (path A below). **Not** via Harmony on stock methods. Full argument, hybrids, and Amdahl: [`SIM_PARALLELISM.md`](SIM_PARALLELISM.md) §5-6. Hot-path catalog: same doc §7.

### 9.2 Realistic on stock main sim (Harmony / config)

| Lever | Mechanism | 1k×10k relevance |
|---|---|---|
| **Tighter AI LOD** | Far skip / alert-aware (EfficientServer today) | Necessary but not sufficient; need extreme hibernate tiers |
| **Path admission** | Max new paths/tick; priority by distance/alert | Critical; path queue is permanent BM at scale |
| **Closest-player cache TTL** | Avoid per-entity global scans | Mandatory habit before population grows |
| **Spawn / sleeper scoping** | Only player-near work | Shrinks “empty continent” cost when players spread |
| **Falling-block → air (optional)** | Delete collapse entity/physics spikes | Local density spike control; fidelity trade |
| **Entity list hygiene** | Ops: junk / Y&lt;0 / abandoned vehicles | Shorter lists; not a default optim feature |
| **Idle TE early-out** | Skip no-op fuel/power work if APM shows TE | Stops content from eating the frame |
| **Mesh / deco / presentation skip** | Dedicated budgets (partially done) | Frees main budget for real sim |
| **Soft-fail feature groups** | Measure one lever at a time | Only way to climb feasibility bands safely |

### 9.3 Hard / rewrite-level on main sim (not a modlet)

| Lever | Why main sim still needs it at 1k×10k |
|---|---|
| **SoA hot zombie state** | Cache + worker-friendly; fat `EntityAlive` graphs die |
| **Spatial hash + reverse observers** | O(local) queries; net interest that scales |
| **Phased workers + intent commit** | Parallel decide, serial apply; stock culture is opposite |
| **Hierarchical / shared path** | One corridor per horde goal, not 10k independent A* |
| **Hard per-bubble + global Full-AI budgets** | Population is a cap, never a work multiplier |
| **Chunk cold storage / residency caps** | Spread 1k players without loading the planet |

### 9.4 What does **not** help main sim

| Idea | Why |
|---|---|
| Thread-per-zombie / Parallel.ForEach EAI | Races, desync, cache thrash; abandoned open-source |
| Parallel SendPackage as optim | Wrong safety; at 1k clients you need **fewer** packages, not parallel fan-out |
| Unbounded concurrent path Task.Run | Stampede under BM |
| Admin panels / Discord / shop | Off the critical path by design |
| Manual `GC.Collect` | Hitch generator |
| **io_uring inside the game process** | Wrong layer for AI tick (next section) |

### 9.5 Measurement that matters for main sim

Under fixed loadgen + APM (not chat FPS):

- Entities in **Full / Medium / Far / Hibernate** tiers
- Path **queue depth** and wait time
- Main-thread time in entity tick vs path wait vs net vs mesh
- Packages **per connection** and aggregate outbound
- Resident **chunk** count (bubble union)
- TE / power stacks if content packs are present
- Save/backup windows blacked out of A/B compares

Climb bands (8→32→64 players, denser AI) before talking about 1k.

## 10. io_uring and this goal

### Short answer

**io_uring does not speed main sim AI.** It is a Linux async I/O interface for **disk and sometimes sockets** when *your* code owns the submission/completion loop. Stock 7DTD main sim is **CPU + managed world mutation + LiteNetLib**, not a custom io_uring game loop.

### Where I/O actually shows up at large scale

| Path | Symptom | io_uring relevant? |
|---|---|---|
| AI / EAI / entity tick | Steady high main CPU | **No** |
| Path queue | Deep queue, workers busy | **No** (already threads; need admission/algorithm) |
| Net serialize + send | High CPU + bandwidth, many clients | **Not via mod io_uring**; need interest/rate budgets or custom net stack (Far) |
| Region load / mesh / view thrash | Hitch when bubbles move or spread | **Indirect**: less thrash + fast disk; not io_uring in Harmony |
| World / player save, BackupMod | Periodic multi-second hitches | **Host**: fast NVMe, schedule; async save only with safe snapshot (Mid, risky) |
| APM export, log ship, external backup | Ops tooling | **Yes** (our tools), zero effect on zombie tick |

### Fit by layer

```text
Main sim (gmUpdate AI/entities) → LOD, caps, cheaper AI, later jobs+commit
Path workers → admission, coalesce, hierarchy (not io_uring)
Net (LiteNetLib / ConnectionManager) → fewer/cheaper packages; rewrite = Far
Disk (regions/saves) → HOST_TUNING + less residency; io_uring only if you rewrite I/O
Ops tools (APM/backup) → io_uring welcome
```

### Verdict for 1k×10k

| Use io_uring? | Where |
|---|---|
| **No** | EfficientServer, main sim, “make zombies faster” |
| **No** (as first move) | Replacing LiteNetLib with custom UDP/io_uring (multi-year net product) |
| **Yes** | Host-side backup/capture pipelines if we own the I/O loop |
| **Maybe later** | A full custom dedicated that **owns** region streaming and implements its own async disk layer (path A rewrite), still secondary to SoA/sim LOD |

If APM shows **hitchy** lag correlated with block/VFS latency, fix **storage placement, save schedule, view/mesh thrash** ([`HOST_TUNING.md`](HOST_TUNING.md), [`OPTIMIZATION_IDEAS.md`](OPTIMIZATION_IDEAS.md) §3). If APM shows **steady** AI/entity CPU, io_uring is a distraction.
